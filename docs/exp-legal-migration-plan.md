# Migration plan: `exp_math` → `exp_legal` (MultiLegalPile)

Plan for adding a new expert group that trains on
[joelniklaus/Multi_Legal_Pile](https://huggingface.co/datasets/joelniklaus/Multi_Legal_Pile),
running alongside the existing math expert group during a transition period.

## What an "expert group" is, in this codebase

A self-contained training task definition. Each lives in `expert_groups/<name>/`
with three files:

| File | Purpose |
|---|---|
| `config.yaml` | Numeric `group_id` (the chain-commit token), `data.dataset_sources` (HF datasets + weights + text column), batch sizes, sequence length, pointer to dataset class |
| `dataset.py` | Subclass of `DefaultStreamingTorchDataset` with a custom `tokenize_and_format` for that data's shape |
| `expert_assignment.json` | MoE routing: which DeepSeek-V2-Lite experts each "group slot" owns. Generated by running the base model on the dataset and recording which experts the router actually selects |

Runtime selection happens via `config.task.expert_group_name` (default
`"exp_math"`). At config load, `_update_by_task()` resolves to
`expert_groups/<name>/config.yaml`, populating `config.task.exp.group_id` and
the dataset pointer.

The `group_id` (int) is the only thing that crosses the chain — written by
miner into `MinerChainCommit.expert_group`, read by validators to know which
miners to evaluate. Validators evaluate only miners whose
`expert_group == config.task.exp.group_id`.

## Strategy: parallel groups (recommended)

Run both `exp_math` and `exp_legal` simultaneously during the transition.
Validators and miners individually opt-in by editing their config's
`task.expert_group_name`. Once enough participants have migrated, deprecate
`exp_math` in a follow-up.

- `exp_math` keeps `group_id=0`
- `exp_dummy` keeps `group_id=1`
- `exp_c4_p02` keeps `group_id=2` (the frozen natural-routing helper slot,
  loaded alongside every active task via `TaskCfg.helper_group_id=2`)
- `exp_legal` gets `group_id=3`

This avoids a coordinated cutover, keeps chain commits backward-compatible, and
lets us A/B compare loss curves before retiring `exp_math`.

The alternative (hard cutover that reuses `group_id=0`) is simpler in steady
state but creates a gap in chain history where `group_id=0` means different
things across cycles, and any miner who misses the deploy ships commits no
validator will score.

## Decisions needed before writing code

These shape the rest of the work — answer them first.

1. **Subset of MultiLegalPile.** The dataset has subsets per
   (language × document-type). Options:
   - `en_all` — just English. Simpler tokenization, faster convergence, narrower scope.
   - `all_all` — full multilingual (24 languages). Needs MoE assignment regenerated on a multilingual sample; sequence length may need bumping.
   - Curated subset (e.g., `en_caselaw + en_legislation`) with custom weights.
2. **Mix in general text?** Pure legal training drifts the model away from
   general language understanding. `exp_math` mixes in C4 at 50/50; consider
   the same for `exp_legal`:
   ```yaml
   - path: "joelniklaus/Multi_Legal_Pile"
     name: "en_all"
     weight: 0.5
   - path: "allenai/c4"
     name: "en"
     weight: 0.5
   ```
3. **Shard-pick policy: register, or defer?** See §3 below — adding
   MultiLegalPile to `_KNOWN_SOURCES` is required for seeded shard-pick
   (currently the default). The "cheap path" is to disable seeded pick for
   `exp_legal` initially; the "right path" is to register the policy properly
   up front.

## 1. Work by component

### 1.1 New `expert_groups/exp_legal/` (~1 day)

```
expert_groups/exp_legal/
├── config.yaml              ← new
├── dataset.py               ← new (likely near-copy of exp_math/dataset.py)
└── expert_assignment.json   ← generated via build_expert_assignment.py
```

**`config.yaml`** (mirror `exp_math/config.yaml`, adjust for chosen subset):

```yaml
group_id: 3
expert_group_name: "exp_legal"
data:
  dataset_sources:
    - path: "joelniklaus/Multi_Legal_Pile"
      name: "en_all"            # see Decisions #1
      weight: 1.0
      text_column: "text"
  per_device_train_batch_size: 1
  batch_size: 4
  sequence_length: 1024   # fleet paradigm (locked DataCfg default); was 4096 pre-tier4
  world_size: 10
  rank: 1
  dataset_class: "expert_groups.exp_legal.dataset:StreamingTorchDataset"
```

**`dataset.py`** — start as a near-copy of `exp_math/dataset.py`. MultiLegalPile
rows have a `text` field already, so the existing CPT-style
`tokenize_and_format` works. Edits likely only if:

- Filtering by jurisdiction/language/document-type (add a row-level filter
  before tokenization)
- Defensive skip for rows with `text == ""`
- Subset-specific weighting (multiple `dataset_sources` entries)

**`expert_assignment.json`** — must regenerate. The MoE router behaves
differently on legal vs math text, so reusing `exp_math`'s assignment would
route legal tokens to math-tuned experts:

```bash
python expert_groups/build_expert_assignment.py \
  --task exp_legal \
  --output expert_groups/exp_legal/expert_assignment.json \
  --num-batches 50 \
  --experts-per-layer 8
```

Runtime: ~30 min on an A6000. Run on a single representative HF shard. Eyeball
the resulting experts-per-layer distribution — if one layer has all 8 experts
routing through 1, the dataset wasn't representative enough; increase
`--num-batches`.

### 1.4 Validator (`connito/validator/`)

**Per-validator action:** edit config, set `task.expert_group_name: "exp_legal"`,
restart.

**Code-level verifications** (no expected changes):

- `run.py:1721` — `active_expert_group_id=config.task.exp.group_id`. ✓
- `round.py:340-341` — reads `expert_group` for cohort seeding. ✓
- `evaluator.py` — uses the same dataset class as miners during baseline eval. ✓
- `cohort_state.py` — `expert_group` is a field on `CohortState`. If a validator
  switches groups mid-cohort, the existing cohort state file will mismatch.
  **Action:** delete the validator's `cohort_state.json` after the group switch
  (or it'll log a warning and rebuild).
- **Checkpoints — use a FRESH state directory (learned live on the pioneer
  validator, 2026-07-11).** Under natural routing the group switch changes the
  model architecture (different trainable expert set), so exp_math-era
  `globalver_*` checkpoints must NOT be resumed: the pioneer validator's first
  exp_legal boot found them, logged `resumed=True`, and overlaid
  exp_math-trained state into the group-3 model (suspect cause of an
  anomalously high baseline). **Action:** bump `run.run_name` (e.g.
  `foundation` → `foundation-legal`) — do NOT edit `ckpt.checkpoint_path`
  directly; `_refresh_paths()` re-derives it as
  `base/<coldkey>/<hotkey>/<run_name>` on every load and silently reverts
  manual edits. The first boot on the new dir must log `resumed=False`.

**Subtlety:** when a validator switches to `exp_legal`, it ignores miners
committing `exp_math` and vice versa. So during transition, a validator on
`exp_legal` will see fewer miners until the miner fleet migrates.

**Deregistration hazard (observed 2026-07-11):** a miner that switches to
`exp_legal` while the stake-majority validators are still on `exp_math`
becomes invisible to them (filtered by `e`), receives no weights, and is
deregistered at the next registration wave — the original uid-121 test miner
was pruned exactly this way. Miners must NOT switch before the validator
majority has; test miners should plan to complete a full commit→score cycle
within their immunity window.

## 2. Validator-consensus shard policy (the longest pole)

`connito/shared/eval_shard_pick.py` has a hard-coded per-source policy registry
(`_KNOWN_SOURCES`) that enumerates the HF sources validators are allowed to
pick shards from in deterministic-consensus mode. Currently registered:

- `(allenai/c4, en)` — `row_count_source="constant"`
- `(nvidia/Nemotron-CC-Math-v1, 4plus)` — `row_count_source="parquet_footer"`

If `dataset_source` isn't in this registry, validators error at module load
(`_validate_policy` at `eval_shard_pick.py:245-249`) or at first eval call when
seeded shard-pick is on (`config.task.exp.data.eval_source_seeded_shard_pick`,
defaults to `True` per `ce3ddc6`).

Adding `exp_legal` requires registering
`(joelniklaus/Multi_Legal_Pile, <subset>)` as a third entry. The policy needs:

- `path_prefix` — HF file path prefix for the subset (e.g., `"en_caselaw/"`)
- `path_suffix` — extensions (likely `(".jsonl.xz",)`)
- `revision` — pinned HF revision SHA (operator-overridable; default needed)
- `row_count_source` — must be `"constant"` (MultiLegalPile is `.jsonl.xz`, not
  parquet, so footer-based row counts don't work)
- `safe_floor_rows`, `min_headroom_rows`, `verified_shard_rows`
  (`{shard_path: row_count}` for every allowed shard)

The row count measurement is offline work: for each shard you want to allow,
count rows once and freeze the count. Reading every `.jsonl.xz` shard is slow
— plan ~2-4 hours for a 24-jurisdiction subset.

Pseudo-code skeleton:

```python
("joelniklaus/Multi_Legal_Pile", "en_caselaw"): _SourceShardPolicy(
    path_prefix="en_caselaw/",
    path_suffix=(".jsonl.xz",),
    revision="<pinned_sha>",
    row_count_source="constant",
    safe_floor_rows=<N>,
    min_headroom_rows=5000,
    verified_shard_rows={
        "en_caselaw/train-00000-of-00037.jsonl.xz": <rows>,
        # ... for every shard
    },
),
```

### Shortcut: defer the policy registration

Set `data.eval_source_seeded_shard_pick: false` in `exp_legal/config.yaml`.
The validator falls back to the older head-of-stream path (no policy needed).

Trade-off: weaker validator-consensus determinism — different validators may
read slightly different windows of the dataset. Acceptable for a launch
period; not acceptable long-term. The seeded path was added to fix exactly
this class of validator divergence.

## 4. Operational notes for the launch period

- **First-cycle baseline jump.** When validators switch tasks, the first
  cycle's `baseline_loss` will be high (the global model has never seen legal
  text). Miners' `delta_loss` will look weird until the global model trains
  in. Plan to discount the first ~24h of rankings as warm-up.
  Communicate this to miners.
- **Tokenizer fit.** Current tokenizer is whatever the base DeepSeek-V2-Lite
  ships with. MultiLegalPile's vocabulary (legal jargon, citations,
  multilingual scripts) may have higher OOV rates than C4 + math. Acceptable
  for CPT but worth measuring perplexity on a held-out legal sample once a
  miner has trained for ~10 cycles.
- **Eval split.** Validators use the same MultiLegalPile shard as miners with
  deterministic shard-pick (or shuffled head-of-stream if shard-pick is
  deferred). Worth being explicit in the migration announcement so miners
  understand what they're being evaluated on.
- **Revision pin escape hatch.** `config.task.exp.data.eval_source_revision_pin`
  is a per-source `dict[str, str]` operator override. If HF pushes a breaking
  change to MultiLegalPile post-launch, every validator can pin to a known-good
  SHA via env, no redeploy required.

## 6. Open questions and follow-ups not in scope

- Should the dashboard API differentiate `exp_math` vs `exp_legal` miners in
  the leaderboard? Currently the leaderboard is per-cycle and doesn't
  distinguish by `expert_group`. A miner on `group_id=3` will be scored only
  by validators also on `group_id=3`, so their `score_avg` will be lower
  during transition simply because fewer validators evaluated them. Worth
  considering a `cohort_group_label` field that includes the expert group.
- The `_specs/` directory referenced in multiple files (`round.py`,
  `run.py`, `round_groups.py`, `config.py`) doesn't exist in the repo.
  Unrelated to this migration but worth a cleanup pass — either restore the
  spec docs or remove the dead references.
- The `expert_groups/exp_math/expert_assignment.json.bk` file is in an older
  schema (outer key = `group_id`, inner pairs = `[layer_id, expert_id]`) than
  the current loader expects (outer key = `layer_id`, inner pairs =
  `[slot, expert_id]`). Stale, safe to delete.
